# Архитектура и текущее состояние

Срез по состоянию на 2026-11-16; план изменений и следующий шаг — в [ROADMAP.md](ROADMAP.md).

## Назначение

IP / PORT Scanner — настольный сканер адресов и портов с отзывчивым графическим интерфейсом.
Текущий прототип проверяет TCP-соединения; пользователь задаёт адреса, порты, таймаут и
параллельность, наблюдает найденные открытые порты и может экспортировать результаты.

## Компоненты и поток данных

1. `src/main.rs` создаёт окно eframe (начальный размер 1180×760, минимум 880×560).
2. `src/app.rs` хранит состояние формы, результаты, прогресс и дескриптор сканирования;
   обрабатывает события и запускает экспорт.
3. `src/ui/sidebar.rs` показывает настройки, пресеты и прогресс, вызывает парсеры перед запуском.
   `src/ui/results.rs` фильтрует и сортирует данные для таблицы, поддерживает плоский вид (`Flat`)
   и древовидную группировку по хостам (`GroupedByHost`); `src/ui/theme.rs` задаёт тему.
   `src/ui/quick_actions.rs` генерирует команды для веб/SSH/БД, формирует контекстное меню и панель-инспектор быстрых действий.
   `src/ui/rtt_view.rs` рассчитывает статистику времени отклика (Min, Avg, Median, p95, Max) и рисует
   адаптивную цветную гистограмму распределения задержек и сводный прогресс-бар.
4. `src/scanner/targets.rs` разбирает и дедуплицирует цели и порты.
   `src/scanner/mod.rs` запускает отдельный поток с Tokio-рантаймом и пулом асинхронных воркеров.
   `src/scanner/probe.rs` выполняет TCP connect с таймаутом и сопоставляет порт с именем сервиса.
   `src/scanner/udp.rs` выполняет UDP-зондирование с RFC-пробами сервисов и трёхпозиционной классификацией исходов.
   `src/scanner/interfaces.rs` выполняет кроссплатформенное обнаружение локальных интерфейсов и форматирование меток.
   При указании адреса привязки (`bind_addr: Option<IpAddr>`), исходящие TCP (`TcpSocket::bind`) и UDP (`UdpSocket::bind`)
   сокеты связываются с локальным адресом источника до вызова подключения/отправки.
   `src/scanner/presets.rs` предоставляет протокол-зависимые наборы портов и алгоритм сжатия диапазонов.
5. Движок передаёт `Started`, `Open` и `Progress` через ограниченный канал Tokio на 4096 событий.
   Итоговое `Finished` или `Failed` передаётся отдельно и читается после закрытия и опустошения
   очереди; это позволяет завершиться при заполненном канале и не потерять уже поставленные
   события. UI обрабатывает не более 1024 событий за кадр и запрашивает немедленный следующий кадр,
   пока есть очередь. Отмена использует `CancellationToken`; уничтожение `ScanHandle` также отменяет
   запуск. `src/export.rs` записывает текущий вектор результатов в CSV или JSON.

Параллельность проверок ограничена настройкой 1–1024; у создаваемого Tokio-рантайма 2–16
потоков. RTT в результатах — время успешного TCP connect, а не ICMP ping или задержка приложения.

## Поддерживаемый ввод и результаты

- По одной цели на строку: одиночный IPv4 или IPv6, CIDR IPv4/IPv6, диапазоны IPv4 (`start-end`)
  и IPv6 (`start_v6-end_v6` до 65 536 адресов), а также DNS-имена хостов (`localhost`, `example.com`, `scanme.nmap.org`);
  пустые строки и строки, начинающиеся с `#`, игнорируются. Идентификаторы зон IPv6 (`%eth0`, `%1`) отклоняются
  с явным диагностическим сообщением (link-local зоны специфичны для интерфейсов и требуют сокетного связывания на уровне интерфейса).
- **Синтаксическая валидация и асинхронный Dual-Stack резолвинг DNS (RFC 1123 / RFC 952):**
  - При редактировании целей в UI разбор выполняется синхронно и строго локально: валидируются правила RFC 1123
    (длина метки 1–63, суммарно $\le 253$ символов, допустимы `[a-zA-Z0-9-_]`, TLD не может быть чисто числовым),
    без вызова сетевых функций DNS. Это гарантирует отсутствие задержек и фризов отрисовки egui.
  - Предпросмотр объёма задания отображает количество прямых адресов и число доменных имён: `Planned scope: 2 targets (1 hostname) × 3 ports (~6 probes)`.
  - При старте сканирования Tokio-рантайм асинхронно разрешает все доменные имена (`tokio::net::lookup_host`)
    с таймаутом 3.0 секунды на запрос и поддержкой мгновенной отмены через `CancellationToken`.
  - Для каждого имени извлекаются все ассоциированные IPv4 (A) и IPv6 (AAAA) адреса; полученные IP объединяются с прямыми
    целями и дедуплицируются в общем множестве `seen: HashSet<IpAddr>`. Ошибки NXDOMAIN или таймаута DNS штатно
    прерывают запуск и отображаются в статусе (`ScanEvent::Failed`). Общее число адресов после резолва проверяется на лимит 65 536.
- Не более 65 536 уникальных адресов на запуск; IPv4 CIDR не шире `/16`, IPv6 CIDR не шире
  `/120`. Адреса CIDR разворачиваются через `ipnet::hosts()`; повторяющиеся адреса удаляются.
- Порты 1–65535, отдельные значения и диапазоны через запятую или пробельные символы;
  повторения удаляются, список сортируется. Есть пресеты Common, Web, Database и Remote.
- Отображаются только успешные подключения. Столбцы: адрес, порт, предполагаемый сервис и RTT.
  Фильтр ищет текст в адресе, порту и сервисе; заголовки управляют сортировкой.
- Экспортирует весь текущий вектор результатов в порядке поступления, независимо от фильтра
  и сортировки. При экспорте во время сканирования файл содержит результаты на момент вызова.
  Форматы содержат `ip`, `port`, `service`, `rtt_ms`.
- Сервис определяется через базу соответствий портов (`ServicesDb`) со временем доступа O(1):
  по умолчанию загружен встроенный срез Nmap/IANA, поддерживается автообнаружение через
  переменную окружения `IP_PORT_SERVICES_PATH`, локальные файлы (`nmap-services`, `services.txt`)
  и загрузка внешних файлов через интерфейс (поддерживаются форматы `nmap-services`, `/etc/services`
  и IANA CSV). Это предположение по номеру порта, а не идентификация протокола по баннеру.
    При включении опции *Grab service banners* движок выполняет чтение приветственного сообщения
    (SSH, FTP, SMTP, VNC, POP3, IMAP) либо отправляет легковесный проверочный запрос (HTTP HEAD).
    Если сервис подтверждён по сигнатуре баннера, он помечается как `service_verified: true` с индикатором `✔` в UI.
    Если ответ не распознан или не поступил, сервис остаётся предположением по базе портов (`service_verified: false`).
    Захват баннеров использует отдельный настраиваемый таймаут (100–5000 мс, по умолчанию 1000 мс) и строго
    ограничен чтением не более 256 байт на соединение, что предотвращает утечки памяти и блокировки.
    Исходы проб классифицируются как успешное TCP-подключение (`Open`), отказ соединения (`Refused`),
    таймаут (`TimedOut`), недоступность сети/хоста (`Unreachable`, например при отсутствии IPv6-маршрута)
    или другая ошибка (`Error`). Отказы, таймауты, недоступность и ошибки хранятся только в агрегированных
    счётчиках, без записи адреса и порта; в UI они показаны как сводка. Отказ соединения — наблюдаемый отказ TCP,
    а таймаут не доказывает, что порт закрыт (причиной могут быть фильтрация или потеря пакетов).
- **UDP-сканирование и неоднозначность исходов (RFC 768 / RFC 1812):**
  - Поддерживается переключение протокола сканирования `[TCP]` / `[UDP]`.
  - В отличие от TCP, протокол UDP не ориентирован на соединение и не производит трехстороннего рукопожатия.
    Движок использует подключенный UDP-сокет (`tokio::net::UdpSocket::connect`), позволяющий ядру ОС ассоциировать
    сокет с целевым адресом и возвращать асинхронные ошибки ICMP Destination Unreachable (Port Unreachable).
  - Ошибки сокетов классифицируются платформонезависимо: `WSAECONNRESET` (10054) на Windows и `ECONNREFUSED` (111, 61)
    на Linux/macOS транслируются в `ProbeOutcome::Refused` (порт закрыт). Ошибки `ENETUNREACH` и `EHOSTUNREACH` транслируются в `ProbeOutcome::Unreachable`.
  - **Трёхпозиционная модель результатов UDP:**
    1. **`Open`:** от целевого сервиса получен явный ответный датаграмм (`recv > 0`). Это строго подтверждённый открытый порт.
    2. **`Open|Filtered`:** отправка пробы завершилась по таймауту без ответа и без ICMP-ошибки. В соответствии с RFC 768 и RFC 1812
       такой исход принципиально неоднозначен: на порту может работать служба, не отвечающая на данный payload, либо пакет
       или обратный ICMP были отфильтрованы брандмауэром. В таблице помечается бейджем `? (open|filtered)` с поясняющим тултипом
       и учитывается в отдельном счётчике `Open|Filtered` в сводке сканирования.
    3. **`Closed` (Refused):** ядро ОС зафиксировало ICMP Port Unreachable. Учитывается в агрегированном счётчике `Closed (refused)`.
  - **Протокольные payload-пробы:** для стандартных UDP-служб отправляются RFC-валидные запросы:
    - DNS (порт 53): стандартный A-query (RFC 1035).
    - NTP (порт 123): клиентский запрос NTPv4 (RFC 5905, 48 байт, режим Client).
    - SNMP (порт 161): SNMPv1 GetRequest (RFC 1157, community `public`, sysDescr).
    - NetBIOS Name Service (порт 137): Node Status Request (RFC 1002, 50 байт).
    - Универсальный fallback: однобайтовый зонд `b"\0"` для минимизации ложных дропов и корректного детектирования эхо-ответов.
  - **ICMP Rate Limiting и ограничение конкурентности:** ядра ОС (в частности Windows и Linux) жестко ограничивают
    частоту генерации ICMP Destination Unreachable. Сканирование UDP на высокой параллельности (>64) приводит к потере
    ICMP-ответов и ложной классификации закрытых портов как `Open|Filtered`. В интерфейсе добавлена рекомендация
    устанавливать параллельность $\le 64$ для UDP, а при переключении с TCP на UDP значение конкурентности автоматически
    снижается до 32, если оно превышало 64.

## Оценка и ограничения сетевых расширений (DNS, интерфейсы, прокси)

В рамках Этапа 4 проведена предреализационная архитектурная оценка (детальный документ: `network_features_evaluation.md`):

1. **DNS-имена (Hostnames / FQDN в целях):**
   - *Критическое ограничение:* вызов системного резолвера (`lookup_host`) непосредственно в UI-потоке недопустим, так как заблокирует отрисовку egui на 0.5–10 секунд при задержках или недоступности DNS.
   - *Архитектурное решение:* синтаксическая валидация (RFC 1123) на этапе ввода в UI без сетевых обращений; фактический асинхронный резолв выполняется в фоне либо при старте сканирования до распределения задач по воркерам.
   - *Семейства адресов (Dual-Stack):* извлечение всех возвращённых A (IPv4) и AAAA (IPv6) записей с дедупликацией в общем пуле `seen: HashSet<IpAddr>` и защитой от превышения лимита `MAX_TARGETS = 65 536`.
   - *Статус:* рекомендовано к реализации в первую очередь.

2. **Выбор сетевого интерфейса (Network Interface Binding):**
   - *Кроссплатформенность и привилегии:* привязка к имени интерфейса (`SO_BINDTODEVICE` на Linux) требует root/`CAP_NET_RAW` и платформозависима (`IP_BOUND_IF` на macOS, `IP_UNICAST_IF` на Windows).
   - *Архитектурное решение:* привязка сокета к локальному IP-адресу выбранного интерфейса (`bind(local_ip:0)`). Это полностью переносимо, безопасно и работает без повышенных привилегий.
   - *Ограничения:* если интерфейс имеет только IPv4-адрес, сканирование IPv6-целей выдаёт немедленный `Unreachable`. При параллельности до 1024 воркеров возрастает риск исчерпания эфемерных портов для конкретного 4-tuple.
   - *Статус:* рекомендовано к реализации во вторую очередь.

3. **Проксирование (SOCKS5 / HTTP CONNECT):**
   - *Критические противоречия:* 
     1. Полная потеря детекции закрытых портов в UDP: ни SOCKS5, ни HTTP CONNECT не пробрасывают ICMP Port Unreachable; HTTP CONNECT вовсе не поддерживает UDP, а SOCKS5 `UDP ASSOCIATE` часто отключен на серверах. Все молчащие порты станут ложно-положительными `Open|Filtered`.
     2. Узкое горлышко производительности: многошаговый хэндшейк прокси на каждое подключение перегрузит локальный прокси при высокой параллельности сканирования и исказит измерение RTT.
   - *Статус:* отложено; реализация в ядре сканера нецелесообразна до завершения базовых сценариев. При необходимости допустим только опциональный экспериментальный TCP-режим с жестким ограничением параллельности ($\le 16$).

## Известные технические ограничения

- Пары адресов и портов выдаются по индексу, а общее количество вычисляется с проверкой
  переполнения. Списки адресов и портов хранятся в памяти. Результаты хранятся только для открытых
  портов и ограничены 100 000 строками; дополнительные открытые исходы считаются, но не сохраняются.
  Закрытые/отказанные, таймауты и прочие ошибки представлены агрегированными счётчиками и не создают
  запись на каждую пробу. Ограничение снижает риск чрезмерного роста памяти, но не ограничивает время
  выполнения сканирования.
- **Пресеты портов с привязкой к протоколам (`scanner::presets`):**
  - Поддерживается контекстный выбор списков портов в зависимости от активного протокола (TCP vs UDP).
  - Для TCP доступны: `Common` (20 портов), `Top 100` (стандартный Nmap Top-100), `Web` (80, 443, 3000, 5000, 8000, 8080, 8443...),
    `Database` (MySQL, Postgres, MSSQL, Oracle, Mongo, Redis), `Remote` (SSH, Telnet, RDP, VNC, WinRM) и `1-1024` (системные).
  - Для UDP доступны: `Common UDP` (15 основных служб: DNS, DHCP, TFTP, NTP, NetBIOS, SNMP, Syslog, OpenVPN, WireGuard),
    `Top 20 UDP`, `VPN / Infra` (IKE, OpenVPN, WireGuard, L2TP) и `Discovery` (mDNS, SSDP, NetBIOS, DHCP).
  - Поддерживается два режима применения: одиночный клик полностью заменяет поле ввода портов, а клик с зажатой клавишей `Ctrl` или `Shift`
    активирует режим объединения без дублирования (`apply_preset`), автоматически сжимая непрерывные последовательности в диапазоны (например, `80-84`).

- Таблица хранит форматированные строки и кэширует видимые индексы; фильтрация/сортировка
  повторяется при изменении результатов, фильтра или порядка сортировки. Сортировка по-прежнему
  синхронная и может быть заметна при очень больших наборах результатов.
- Поток событий ограничен бюджетом в 1024 события на кадр. Нагрузочный замер на 20 000 синтетических
  результатов (AMD Ryzen 5 5600X, 32GB RAM, Windows 10 x64) подтверждает высокую отзывчивость:
  приём 20k событий за 51.7 мс (~386 500 событий/с), сортировка за 1.3–3.8 мс, текстовый фильтр за 19.3 мс,
  среднее время полного кадра egui 7.35 мс (136 FPS, p95 = 6.03 мс), что с запасом укладывается в 16.6 мс (60 FPS).
- Прогресс передаётся раз в 50 завершённых проверок и может временно отставать. События от
  параллельных воркеров могут поступать не по порядку, поэтому UI сохраняет наибольшее значение.
  Во время сканирования UI показывает elapsed, среднюю скорость завершённых проверок и ETA,
  вычисленную по этой средней скорости; оценки приблизительные. При отмене проверка, результат
  которой ещё не поставлен в очередь, может не учитываться.
- Обработаны и покрыты тестами ошибки инициализации Tokio-рантайма, паники воркера,
  создания системного потока и отмены активной пробы. Ручная smoke-проверка
  Windows подтвердила отображение UI, предпросмотр и валидацию (порт 0 отклоняется), остановку,
  фильтрацию и экспорт: CSV/JSON совпали и содержали все 13 найденных результатов при активном
  фильтре. Автоматические тесты покрывают масштабирование окна (880×560 .. 4K), DPI-скейлинг (100%–200%),
  контрастность палитры по стандарту WCAG AAA (12.86:1 при sRGB/Display P3 и 9.68:1 при Apple linear gamma),
  динамическую схему модификаторов (Ctrl/Cmd), полную клавиатурную навигацию по результатам (стрелки Up/Down, Home, End,
  Enter/Space) и клавиатурные сочетания на схемах Linux и macOS (Enter, Escape, C, F, E, Shift+E).
  Таблица результатов визуально очищена от вертикальных разделителей колонок (без сеточного шума).
  Ручной прогон GUI на физических Linux/macOS ещё не выполнялся.
- Профили настроек хранятся в версионируемом JSON (версия 1): цели, порты, таймаут, конкурентность и протокол (`"tcp"` / `"udp"`).
  Для обратной совместимости при отсутствии поля `protocol` в ранее сохранённых профилях используется значение по умолчанию `"tcp"`.
  Загрузка отклоняет неизвестные поля/версии, некорректные цели/порты и значения вне диапазонов UI;
  состояние приложения обновляется только после успешной полной проверки. Файловые операции профилей выполняются синхронно.
- Экспорт получает снимок результатов в момент вызова, независимо от фильтра/сортировки; запись CSV/JSON с потоковым
  экранированием выполняется в отдельном системном потоке через `BufWriter`. Формат версионирован (схема v1):
  - **CSV v1:** заголовок `CSV_HEADER_V1 = "ip,port,service,rtt_ms"`, экранирование по RFC 4180.
  - **JSON v1:** массив объектов с типизированными полями `ip` (str), `port` (u16), `service` (str), `rtt_ms` (f64), а также расширенными полями `protocol` ("tcp" / "udp") и `state` ("open" / "open|filtered"), экранирование по RFC 8259.
  - **Совместимость:** будущее расширение схемы (v2+) гарантирует сохранение базовых полей и добавление новых атрибутов только в конец строк/объектов.
  UI опрашивает завершение, показывает ошибку I/O или ссылку на сохранённый файл; одновременный второй экспорт блокируется.
  Timestamp-имя по умолчанию: `scan_results_YYYYMMDD_HHMMSS.{ext}`. Нагрузочный тест подтверждает изолированность снимка (добавление 500 результатов во время записи) и сохранение статуса сканирования при записи 20 000 строк.
- Автоматические тесты (71 тест; Windows, 2026-11-17) покрывают ввод/предпросмотр, диапазоны IPv4 и IPv6,
  DNS-имена хостов (синтаксическую валидацию RFC 1123, нормализацию регистра, локальное разрешение `localhost`,
  дедупликацию с IP-адресами, диагностику ошибок резолвинга/NXDOMAIN, таймауты и отмену во время DNS-запроса),
  диагностику zone identifiers, проверку loopback `::1`, профили (round-trip, версия/поля, валидацию, обратную совместимость по протоколу и атомарное применение),
  экспорт на больших наборах во время сканирования, форматную совместимость CSV/JSON v1, экранирование спецсимволов,
  ошибки файловой системы и генерацию timestamp-имён, генерацию заданий, классификацию исходов проб (`Open`, `Refused`,
  `TimedOut`, `Unreachable`, `Error`), агрегирование без хранения закрытых результатов и лимит 100 000 открытых результатов,
  опциональный захват баннеров сервисов (greeting баннеры SSH/FTP/SMTP, probe-баннеры HTTP, таймауты молчащих серверов без потери открытого статуса,
  очистку и усечение до 160 символов, определение протоколов и сквозной сбор в сканере),
  UDP-зондирование (генерацию RFC-запросов DNS/NTP/SNMP/NetBIOS, классификацию ошибок сокетов `WSAECONNRESET`/`ECONNREFUSED`,
  детектирование ответов датаграмм как `Open`, классификацию таймаута как `OpenFiltered` и сквозное UDP-сканирование в рантайме),
  локальные TCP/UDP-порты, отмену при заполненном канале и в активной пробе, повторный запуск, ошибки рантайма,
  создания потока и воркера, монотонность прогресса, инвалидацию кэша таблицы, нагрузочные замеры,
  масштабирование/DPI, контрастность WCAG при разных профилях гаммы, клавиатурную навигацию и сочетания Linux/macOS,
  всплывающие toast-уведомления, а также парсинг форматов баз сервисов (nmap-services, /etc/services, IANA CSV)
  и динамическое переопределение базы сервисов. Нет физической GUI-проверки на Linux/macOS.

## Непрерывная интеграция, выпуск и платформенная поддержка

- **MSRV (Minimum Supported Rust Version):** зафиксирован на `Rust 1.95.0` (`rust-version = "1.95"` в `Cargo.toml`, обусловлен зависимостями экосистемы egui/eframe 0.37). Редакция: `edition = "2024"`.
- **Автоматический CI пайплайн (`.github/workflows/ci.yml`):**
  - Шаг `Formatting`: запуск `cargo fmt --check` на `ubuntu-latest`.
  - Шаг `Test & Clippy`: матрица по целевым операционным системам (`ubuntu-latest`, `windows-latest`, `macos-latest`).
    На Linux автоматически устанавливаются зависимости `libxkbcommon-dev`, `libwayland-dev`, `libgl1-mesa-dev`, `libx11-dev`, `libxcursor-dev`, `libxi-dev`, `libxrandr-dev`.
    Выполняются `cargo clippy --all-targets -- -D warnings`, `cargo test --all-targets`, а также сборка релизного артефакта `cargo build --release` с выгрузкой в actions artifacts.
  - Шаг `MSRV`: проверка компиляции `cargo check --all-targets` на строго зафиксированной версии компилятора `dtolnay/rust-toolchain@1.95.0`.
- **Автоматический релизный пайплайн (`.github/workflows/release.yml`):**
  - Запускается по тегам `v*.*.*`.
  - Матричная кросс-компиляция под 4 целевые платформы:
    - Windows x64 (`x86_64-pc-windows-msvc`) -> `.zip`
    - Linux x64 (`x86_64-unknown-linux-gnu`) -> `.tar.gz`
    - macOS Apple Silicon (`aarch64-apple-darwin`) -> `.tar.gz`
    - macOS Intel (`x86_64-apple-darwin`) -> `.tar.gz`
  - Упаковывает бинарные файлы вместе с `README.md`, `LICENSE` и `CHANGELOG.md`.
  - Вычисляет контрольные суммы `SHA256SUMS.txt` и публикует GitHub Release через `softprops/action-gh-release@v2`.
- Руководство по установке, зависимостям и шагам сборки доступно в [PACKAGING.md](PACKAGING.md).
- История изменений проекта ведётся по стандарту Keep a Changelog в [CHANGELOG.md](CHANGELOG.md).

## Локальная проверка

```bash
cargo fmt --check
cargo test
cargo clippy --all-targets -- -D warnings
cargo run
```

Для ручной проверки используйте контролируемые локальные сервисы, в том числе `127.0.0.1` и,
при доступности IPv6, `::1`. Проверяйте запуск, прогресс, остановку, повторный запуск, фильтр,
сортировку и экспорт. GUI и работа на каждой платформе требуют отдельной ручной проверки;
успешные модульные тесты сами по себе её не заменяют.
