# Архитектура и текущее состояние

Срез по состоянию на 2026-11-16; план изменений и следующий шаг — в [ROADMAP.md](ROADMAP.md).

## Назначение

IP / PORT Scanner — настольный сканер адресов и портов с отзывчивым графическим интерфейсом.
Текущий прототип проверяет TCP-соединения; пользователь задаёт адреса, порты, таймаут и
параллельность, наблюдает найденные открытые порты и может экспортировать результаты.

## Компоненты и поток данных

1. `src/main.rs` создаёт окно eframe (начальный размер 1180×760, минимум 880×560).
2. `src/app.rs` хранит состояние формы, результаты, прогресс и дескриптор сканирования;
   обрабатывает события и запускает экспорт.
3. `src/ui/sidebar.rs` показывает настройки, пресеты и прогресс, вызывает парсеры перед запуском.
   `src/ui/results.rs` фильтрует и сортирует данные для таблицы; `src/ui/theme.rs` задаёт тему.
4. `src/scanner/targets.rs` разбирает и дедуплицирует цели и порты.
   `src/scanner/mod.rs` запускает отдельный поток с Tokio-рантаймом и пулом асинхронных воркеров.
   `src/scanner/probe.rs` выполняет TCP connect с таймаутом и сопоставляет порт с именем сервиса.
5. Движок передаёт `Started`, `Open` и `Progress` через ограниченный канал Tokio на 4096 событий.
   Итоговое `Finished` или `Failed` передаётся отдельно и читается после закрытия и опустошения
   очереди; это позволяет завершиться при заполненном канале и не потерять уже поставленные
   события. UI обрабатывает не более 1024 событий за кадр и запрашивает немедленный следующий кадр,
   пока есть очередь. Отмена использует `CancellationToken`; уничтожение `ScanHandle` также отменяет
   запуск. `src/export.rs` записывает текущий вектор результатов в CSV или JSON.

Параллельность проверок ограничена настройкой 1–1024; у создаваемого Tokio-рантайма 2–16
потоков. RTT в результатах — время успешного TCP connect, а не ICMP ping или задержка приложения.

## Поддерживаемый ввод и результаты

- По одной цели на строку: одиночный IPv4 или IPv6, CIDR IPv4/IPv6, диапазон IPv4; пустые строки
  и строки, начинающиеся с `#`, игнорируются. Имена хостов и диапазоны IPv6 не поддерживаются.
- Не более 65 536 уникальных адресов на запуск; IPv4 CIDR не шире `/16`, IPv6 CIDR не шире
  `/120`. Адреса CIDR разворачиваются через `ipnet::hosts()`; повторяющиеся адреса удаляются.
- Порты 1–65535, отдельные значения и диапазоны через запятую или пробельные символы;
  повторения удаляются, список сортируется. Есть пресеты Common, Web, Database и Remote.
- Отображаются только успешные подключения. Столбцы: адрес, порт, предполагаемый сервис и RTT.
  Фильтр ищет текст в адресе, порту и сервисе; заголовки управляют сортировкой.
- Экспортирует весь текущий вектор результатов в порядке поступления, независимо от фильтра
  и сортировки. При экспорте во время сканирования файл содержит результаты на момент вызова.
  Форматы содержат `ip`, `port`, `service`, `rtt_ms`.
- Сервис определяется через базу соответствий портов (`ServicesDb`) со временем доступа O(1):
  по умолчанию загружен встроенный срез Nmap/IANA, поддерживается автообнаружение через
  переменную окружения `IP_PORT_SERVICES_PATH`, локальные файлы (`nmap-services`, `services.txt`)
  и загрузка внешних файлов через интерфейс (поддерживаются форматы `nmap-services`, `/etc/services`
  и IANA CSV). Это предположение по номеру порта, а не идентификация протокола по баннеру.
  Ошибки подключения и таймауты сейчас не различаются и в результатах не представлены.

## Известные технические ограничения

- Пары адресов и портов выдаются по индексу, а общее количество вычисляется с проверкой
  переполнения. Сами списки адресов, портов и открытых результатов всё равно хранятся в памяти;
  большие задания могут выполняться долго или накапливать много результатов.
- Таблица хранит форматированные строки и кэширует видимые индексы; фильтрация/сортировка
  повторяется при изменении результатов, фильтра или порядка сортировки. Сортировка по-прежнему
  синхронная и может быть заметна при очень больших наборах результатов.
- Поток событий ограничен бюджетом в 1024 события на кадр. Нагрузочный замер на 20 000 синтетических
  результатов (AMD Ryzen 5 5600X, 32GB RAM, Windows 10 x64) подтверждает высокую отзывчивость:
  приём 20k событий за 51.7 мс (~386 500 событий/с), сортировка за 1.3–3.8 мс, текстовый фильтр за 19.3 мс,
  среднее время полного кадра egui 7.35 мс (136 FPS, p95 = 6.03 мс), что с запасом укладывается в 16.6 мс (60 FPS).
- Прогресс передаётся раз в 50 завершённых проверок и может временно отставать. События от
  параллельных воркеров могут поступать не по порядку, поэтому UI сохраняет наибольшее значение.
  Во время сканирования UI показывает elapsed, среднюю скорость завершённых проверок и ETA,
  вычисленную по этой средней скорости; оценки приблизительные. При отмене проверка, результат
  которой ещё не поставлен в очередь, может не учитываться.
- Обработаны и покрыты тестами ошибки инициализации Tokio-рантайма, паники воркера,
  создания системного потока и отмены активной пробы. Ручная smoke-проверка
  Windows подтвердила отображение UI, предпросмотр и валидацию (порт 0 отклоняется), остановку,
  фильтрацию и экспорт: CSV/JSON совпали и содержали все 13 найденных результатов при активном
  фильтре. Автоматические тесты покрывают масштабирование окна (880×560 .. 4K), DPI-скейлинг (100%–200%),
  контрастность палитры по стандарту WCAG AAA (12.86:1 при sRGB/Display P3 и 9.68:1 при Apple linear gamma),
  динамическую схему модификаторов (Ctrl/Cmd), полную клавиатурную навигацию по результатам (стрелки Up/Down, Home, End,
  Enter/Space) и клавиатурные сочетания на схемах Linux и macOS (Enter, Escape, C, F, E, Shift+E).
  Таблица результатов визуально очищена от вертикальных разделителей колонок (без сеточного шума).
  Ручной прогон GUI на физических Linux/macOS ещё не выполнялся.
- Экспорт строит файл целиком в памяти и записывает его синхронно из UI с генерацией timestamp-имени по умолчанию
  (`scan_results_YYYYMMDD_HHMMSS.{ext}`); ссылка на сохранённый файл в панели статуса кликабельна и открывает
  проводник ОС. Формирование CSV и JSON выполняется вручную; при появлении произвольных текстовых полей потребуется экранирование.
- Автоматические тесты (36 тестов) покрывают ввод/предпросмотр, экспорт и генерацию timestamp-имён, генерацию заданий, локальные
  TCP-порты, отмену при заполненном канале и в активной пробе, повторный запуск, ошибки рантайма,
  создания потока и воркера, монотонность прогресса, инвалидацию кэша таблицы, нагрузочные замеры,
  масштабирование/DPI, контрастность WCAG при разных профилях гаммы, клавиатурную навигацию и сочетания Linux/macOS,
  всплывающие toast-уведомления, а также парсинг форматов баз сервисов (nmap-services, /etc/services, IANA CSV)
  и динамическое переопределение базы сервисов. Нет физической GUI-проверки на Linux/macOS и полноценного IPv6-пути.

## Локальная проверка

```bash
cargo fmt --check
cargo test
cargo clippy --all-targets -- -D warnings
cargo run
```

Для ручной проверки используйте контролируемые локальные сервисы, в том числе `127.0.0.1` и,
при доступности IPv6, `::1`. Проверяйте запуск, прогресс, остановку, повторный запуск, фильтр,
сортировку и экспорт. GUI и работа на каждой платформе требуют отдельной ручной проверки;
успешные модульные тесты сами по себе её не заменяют.
