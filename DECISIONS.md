# IP_PORT — принятые и отложенные проектные решения

Дата фиксации: **2026-11-21**. Статус: **продуктовое и архитектурное согласование**, а не завершённая реализация. Текущий стабильный выпуск — [v0.4.0](https://github.com/uzbatsu-beep/IP_PORT/releases/tag/v0.4.0).

Этот реестр сохраняет явно согласованные решения и вопросы для следующего обсуждения. Не считайте запись в таблице задачей, автоматически разрешённой к разработке или слиянию.

## Утверждено

| ID | Решение | Практическое следствие |
|---|---|---|
| DEC-001 | IP_PORT — компактное кроссплатформенное приложение с локальным хранением, быстрым сканированием, инженерной идентификацией, историей изменений и контролируемыми методами проверки IT/OT-инфраструктуры | Не превращать IP_PORT в тяжёлую SCADA, облачный сервис или агрессивный массовый сканер |
| DEC-002 | **Универсальная карточка устройства утверждена** как центральный объект UI | Разделы: обзор, интерфейсы/протоколы, компоненты, история, диагностика/источники; отраслевые расширения без новых несвязанных экранов |
| DEC-003 | **Модель данных нового поколения утверждена** на концептуальном уровне | `Asset`, `DeviceIdentity`, `NetworkInterface`, `LogicalDevice`, `ServiceEndpoint`, `Observation`, `DeviceRelationship`, `ScanSession`, `DeviceProfile`, `IndustrialProtocol`; конкретная SQL-схема отдельно |
| DEC-004 | **Многоканальная идентификация устройств** — ключевое направление, особенно для АСУ ТП | Разделять импортированные описания, наблюдения, сведения мастера/шлюза, подтверждение протоколом и ручную верификацию; не считать порт доказательством модели |
| DEC-005 | **Модульная архитектура следующего поколения согласована** | UI/egui → контроль области/диспетчер задач → discovery/enrichment/passive import → локальное хранилище активов → отчёты/интеграции |
| DEC-006 | **Обновлённый концептуальный roadmap v0.4.1–v0.8.x согласован** | Этапы: стабилизация; история/карточки/diff; расширенное обнаружение; промышленная идентификация; расширяемость. Очерёдность отдельных PR ещё не согласована |
| DEC-007 | **Сейчас не разрабатывать отдельный большой OT Safety Policy Engine** | Сохранять уже имеющиеся scope/exclusions, управляемую нагрузку и явную границу read-only vs управление; вводить локальные ограничения по мере появления активных адаптеров |
| DEC-008 | Не фокусироваться на raw-SYN/массовых сканерах, автономных управляющих AI-командах, автоматическом исполнении потенциально опасных скриптов и тяжёлой инфраструктуре | Не включать в ближайший backlog без отдельного запроса |
| DEC-009 | Все распространённые промышленные семейства должны **представляться каталогом**, но «известен протокол» ≠ «реализован/испытан драйвер» | Обозначать уровни: Catalogued / Offline / Passive / Active-ID / Validated; не заявлять универсальный активный доступ к любому устройству |
| DEC-010 | 2026-11-26: UI-03, вариант C (Engineering Workbench) утверждён | Верхняя и нижняя панели, узкая вертикальная навигация с иконками, контекстная рабочая панель, центр Devices по умолчанию (Ports доступен), карточка справа; переключаемый RU/EN. Детализация — [UI_WORKSPACE.md](UI_WORKSPACE.md) |
| DEC-011 | 2026-11-26: UI-03.2 утверждён | Сворачиваемая векторная навигация: Discovery, Devices, Diagnostics, Knowledge Base, Reports, Settings; старт Discovery с Devices; сохранение языка; состояние сканера общее и не зависит от разделов. Начальный офлайн-каталог промышленной связи — [INDUSTRIAL_PROTOCOLS.md](INDUSTRIAL_PROTOCOLS.md) |

## Что это не означает

Согласование концепции **не разрешает автоматически запускать активные запросы** в производственной сети, объявлять неизвестное устройство подтверждённым PLC, менять код без отдельного плана или публиковать релиз. Сведения из офлайн-файлов — описание *типа*, а не доказательство физического присутствия конкретной единицы оборудования. Все будущие изменения проходят обычный PR и CI.
